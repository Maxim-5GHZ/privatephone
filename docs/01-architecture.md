# 01 — Архитектура

Общее устройство комплекса, слои защиты, жизненный путь пакета, P2P-медиа и
навигация по исходникам.

## 1. Общая картина

```
┌─────────────────────────── УЗЕЛ (машина оператора) ───────────────────────────┐
│                                                                                │
│  data/  ─ р я д о м  с  б и н а р н и к о м ─                                 │
│    vault.db        зашифрованный AES-256-GCM SQLite (все данные)              │
│    pp.local        половина-A мастер-ключа (на диске)                         │
│    admin.pem       ключ оператора (для выпуска абонентов)                     │
│    ca.crt/ca.key   внутренний CA меша                                         │
│    tls.crt/tls.key HTTPS/WSS сертификат узла                                  │
│                                                                                │
│  бинарь pp (Go, один файл)                                                     │
│   ├─ REST /api/v1/*    подписанные запросы (метки, сообщения, тревоги, CA…)   │
│   ├─ WS   /api/v1/ws   подписанные фреймы (широковещание, store-and-forward)  │
│   ├─ SPA  /            React-интерфейс (встроен через go:embed)               │
│   └─ /tiles/           офлайн-карта (встроенные PNG, OSM-проекция)            │
│                                                                                │
│  RAM процесса: мастер-ключ (mlock, только RAM), рабочий SQLite в /dev/shm     │
│  Watchdog: USB-половина извлечена → ключ затёрт → процесс завершён (~1с)      │
└──────────────┬─────────────────────────────────────────────────────────────────┘
               │  HTTPS / WSS / REST  (localhost или LAN, точка доступа Wi-Fi)
               ▼
┌────────────────────────── АБОНЕНТСКИЕ УСТРОЙСТВА (браузеры) ──────────────────┐
│  React SPA: карта меток, чат, тревоги, звонок, рация                           │
│  WebCrypto: ECDSA P-256 подпись всех пакетов (PKCS#8, ключ с флешки)          │
│  E2EE:      ECDH-конверты — сервер содержит только шифротексты                 │
│  Медиа:     WebRTC P2P (браузер↔браузер), SFrame поверх DTLS-SRTP             │
└─────────────────────────────────────────────────────────────────────────────────┘
```

Ключевая идея: **узел — это «почтовое отделение», а не «коммутатор доверия»**.
Он проверяет подписи и маршрутизирует пакеты, но никогда не расшифровывает
содержимое и никогда не проксирует голос/видео. Медиа всегда P2P между
браузерами; сигналинг (SDP/ICE/SFrame-ключ) релеится через узел, но запечатан
в E2EE-конвертах.

## 2. Слои защиты (почему «защищено»)

Четыре независимых слоя закрывают разные уровни протокола:

| # | Слой | Что защищает | От кого | Средство |
|---|---|---|---|---|
| 1 | **TLS/WSS** | транспорт REST/WS | прослушиватель сети, MITM на пути | самоподписанный серт узла + CA из `data/ca.crt` (`cert.go`) |
| 2 | **ECDSA-подпись** | каждый пакет: целостность + аутентичность | подделка чужим callsign, подмена, повтор | подпись P-256 по канону + replay-guard (`sign.go`, `protocol.go`) |
| 3 | **E2EE-конверты** | содержимое (текст, координаты, зоны, тревоги) | сам узел/оператор БД, прослушиватель журнала | эфемерный ECDH на сообщение, AES-256-GCM (`e2ee.ts`) |
| 4 | **SFrame** | RTP-медиа звонка/рации | узел, компрометированный участник | покадровый AES-GCM поверх DTLS-SRTP (`sframe.ts`) |

Важно: слои работают **независимо** — утёк TLS не открывает содержимое (оно
E2EE), компрометация статического ключа абонента не вскрывает прошлые конверты
(эфемерные ключи, forward secrecy), а перехват одного RTP-кадра не вскрывает
соседние (производные ключи на каждый кадр).

## 3. Путь пакета от абонента до всех

Разберём на примере текстового сообщения (°1), затем — меток/тревог (°2).

```
Абонент A (браузер)
  1. encrypt(recipients, plaintext)          e2ee.ts:156  → E2EE-конверт {v2,epub,iv,c,k[]}
  2. signPacket('message', data)             signing.ts:84 → подпись ECDSA по канону
  3. apiPost('/api/v1/messages', …)          client.ts:4  → REST с заголовками X-Sender/X-Signature/…

Узел (сервер)
  4. decodeEnvelope (заголовки→Envelope)    server.go:134
  5. middleware signed → Verifier.Verify     protocol.go:73
       подпись по реестру (SubscriberLookup) → replay-guard → (опц. калибровка часов)
  6. IngestMessage                           ingest.go:105
       парсит {recipient, body, enc}; при enc тело заменяется конвертом (opaque)
  7. st.AddMessage(...)                      store.go:453 (SQLite в /dev/shm)
  8. h.journal(...) → packets таблица        import.go:15 (hash-цепочка, tamper-evident)
  9. h.deliver(...)                          relay.go:90  (broadcast / direct / группа)
       ↕ writePump → WebSocket каждому адресату (кроме отозванных)

Абоненты B, C (браузеры)
 10. handleMsg('message')                    useMesh.ts:351
 11. useDecrypted → decrypt(...)             e2ee.ts:188 (только для своих записей k[])
```

Сигнальные события (звонки `call_*`/`ice`, рация `ptt_*`) **не журналируются и
не сохраняются** — узел релеит их «байт-в-байт» только адресату(там):
`relay.go:11-69`. Получатель (браузер) сам верифицирует подпись отправителя —
узел не является Trusted Third Party даже для сигналинга.

## 4. Store-and-forward (офлайн-доставка)

Узел — единственная постоянная точка, поэтому он хранит недоставленное:

- Все входящие подписанные пакеты записываются в журнал `packets`
  (`AddPacket`, store.go:524) с флагом `delivered`.
- После `hello` (подписанная аутентификация WS-сессии) клиенту отдаются
  `snapshot` (текущее состояние карты/чата/тревог/онлайн) + `packets`
  (пакет всего, что ему адресовано и ещё не подтверждено): `pushBacklog`,
  hub.go:113-145.
- Очередь «что мне не отдали» строится запросом `UndeliveredPacketsFor(ctx,
  callsign)` (store.go:690) — бродкаст + адресованные мне + мои собственные.
- Получив пачку, клиент шлёт подписанный `ack {ids}` → `MarkDelivered`
  (store.go:710), узел ставит `delivered=1`. Идемпотентно, безопасно к повторам.

```
A ---packet---> узел ----delivered---> B (сейчас)
                 │
                 └----(B офлайн)---> B просыпается: hello → snapshot + packets →
                                          ack{ids} → delivered=1
```

## 5. Звонки и рация (P2P, медиа мимо узла)

### Звонок 1:1
```
A: new RTCPeerConnection({iceServers:[]})          webRTC.ts:205 (только host-кандидаты, ЛВС)
A: call_invite {sdp, sframe}  --E2EE-конверт+подпись--> узел --relay--> B
B: call_accept {sdp}          --E2EE--> узел --> A
A/B: ice                      (кандидаты, одновременно с sdp)
A/B: SFrame поверх DTLS-SRTP; ключ получен от A в call_invite
A/B: call_bye при завершении
```
Узел видит в `call_invite` только поле маршрутизации `to`; SDP/ICE/SFrame-ключ —
opaque-конверт (`signal.ts:1-5`, `webRTC.ts:90`). Если B офлайн — A получает
`call_error {to, error:"offline"}` (relay.go:20-24).

### Рация PTT (полный меш, до MAX_MEMBERS участников)
```
A: start(targets) → ptt_start {n=сессия, sframe-ключ} --E2EE--> узел --> все + A
B,C: join(...) → обмениваются ptt_offer/answer/ice с каждым (+A)
A: setTalking(true) → replaceTrack микрофона → ptt_talking {talks:A} → все
B,C: ontrack → MediaStream → <audio>; не-говорящие приглушены (volume=0)
A: end() → ptt_end + закрытие всех PEER-подключений
```
Каждый участник держит RTCPeerConnection с каждым (fulness-mesh, ptt.ts:49).
Говорящий один — только его микрофон слышен всем. Сессия эфемерна, узел её
не журналирует (`ptt.ts:8`, relay.go:33-35).

## 6. Отображение карты и офлайн-тайлы

- Тайлы `/tiles/{osm|sat}/{z}/{x}/{y}.png`: сначала `data/tiles/` (custom/докачка),
  потом embed `internal/web/tiles` (`web.go:13`, `server.go`), проекция Web-Mercator
  (OSM). По умолчанию — процедурные «заглушки» z0–5 (`cmd/gentiles`,
  `--skip-existing` не затирает скачанное); область докачивается сервером при
  наличии интернета (`POST /api/v1/admin/tiles/fetch`, z0–16, cap ~20k). Нет
  тайла — прозрачный fallback-PNG (карта не рвётся). См. `04-deployment`.
- Карта в браузере — OpenLayers (`Map`/`View` EPSG:3857, два `TileLayer/XYZ`
  osm+sat с переключателем, `VectorLayer` для маркеров/зон, попапы — React через
  `Overlay`, attribution OSM/Esri обязательно).
- Координаты маркеров/зон — `[lat, lon]` (WGS-84); в ol конвертируются через
  `fromLonLat`/`toLonLat`.

## 7. Аутентификация браузера

- Логин = выбор файла `<callsign>.prv.pem` (PKCS#8, принесённого на флешке) +
  ввод позывного. Ключ импортируется:
  - как **ECDSA** для подписи (`signing.ts:36-54`);
  - повторно как **ECDH** для E2EE (`e2ee.ts:47-61`, `bootE2EE`).
- Ключ живёт **только в памяти страницы** (модульная переменная), не пишется в
  localStorage (`Login.tsx:86-88`). Ушёл вкладку → ключ утерян → логин заново.
- Right admin не управляется: у админа его собственный абонентский `.prv.pem`,
  роль `admin` берётся из реестра (`subscribers[].role`), сервер требует
  `signedAdmin` для операций CA/журнала (`server.go:114-132`).
- «Отпечаток» ключа: `SHA-256(SPKI)` → 8 hex — показывается при логине, чтобы
  оператор сверил, что на флешке правильный ключ (`e2ee.ts:101-111`).

## 9. Границы и допущения

- **ЛВС/офлайн-сценарий**: узел — точка доступа для клиентов сети; media P2P
  только в одной ЛВС (`iceServers: []`, host-кандидаты, webRTC.ts:206) — за NAT
  звонки/рация не работают без TURN (осознанно: нет внешних сервисов).
- **Не интернет-система**: журнал хранится на узле; межсетевой обмен — только
  sneaker-net («мешки»). См. `05-usecases` §7.
- **Один узел**: реестр абонентов и подписи привязаны к одному узлу; другой узел
  (свой меш) имеет свой реестр (распространение мешков синхронизирует события,
  но не реестр-ключи автоматически).
- **Нет ротации ключей**: публичные ключи абонентов статические; при
  компрометации — отзыв (CRL) и выпуск нового ключа, events журналируются.
