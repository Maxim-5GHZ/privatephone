# 05 — Варианты использования

Роли, повседневные сценарии, действия админа, межсетевой обмен (sneaker-net),
аварийные ситуации и поведение при офлайне.

## 1. Роли и «кто что может»

| Роль | Права | Доступ в UI |
|---|---|---|
| `admin` | всё, что у operator + выпуск/отзыв абонентов, экспорт/импорт журнала, статистика, удаление/очистка любых объектов | вкладки Абоненты + Журнал + Импорт |
| `operator` | подпись пакетов, свои метки/сообщения/тревоги/зоны, удаление/очистка ТОЛЬКО своих | карта, сообщения, рация, звонки |

- Права проверяет сервер (среднее-ware `signedAdmin`, server.go:114-132;
  delete/clear — по ownership, ingest.go:91-93, 211-213, 318-320).
- Все операции с абонентами журналируются. Вход админа — его собственный
  `.prv.pem`; роль берётся из реестра (см. `01-architecture` §7).

## 2. Жизненный цикл абонента

1. **Выпуск**: админ → «Абоненты» → позывной + роль → браузер показывает
   приватный ключ `<callsign>.prv.pem` — **скачивается один раз**, копируется
   на флешку абонента (`handleCreateSubscriber`, useMesh.ts:543-553). На сервере
   хранится только публичный ключ.
2. **Вход**: абонент открывает `https://<ip>:8080`, выбирает `.prv.pem` и
   вводит позывной; ключ импортируется как ECDSA (подпись) + ECDH (E2EE),
   живёт только в памяти страницы.
3. **Отзыв (CRL)**: админ → «Отозвать». Эффекты немедленные и многослойные
   (см. `02-cryptography` §3): реестр, in-memory CRL, доставка, кик сессии.
4. **Возврат**: админ → «Вернуть» (unrevoke).
5. **Утеря ключа/флешки абонента**: отзыв + выпуск нового ключа (старый
   перестаёт работать instantly; журнал хранит обе истории).

## 3. Ежедневная работа группы

### Карта меток (MapView)
- Ставишь метку на карте: тип (Свои/Противник/Нейтральная/РЭБ/Раненый/Люди/
  Техника/Встреча/Другое), координаты, описание; скрытие старых (>24ч).
- Метку может редактировать/удалять **только автор или admin**; узел хранит
  содержимое шифрованным (сервер видит `type='enc'`).
- Зоны: рисование полигона кликами, имя/цвет; право — автор/admin.

### Тревоги (SOS / СБОР / Инфо)
- Кнопка на карте → `alert` broadcast; у всех баннер с пульсацией и звуком
  (WebAudio).
- «Принял» → `alert_ack` (аудита-запись в `@system`, видна в списке acks).
- «Отбой» → `alert_clear` (только автор или admin).
- Узел воспроигрывает тревоги офлайн-абонентам при их подключении (backlog).

### Сообщения (чат)
- «Общий» (broadcast), «директ» (callsign), «группа» (массив) — все получатели
  должны иметь ключи друг друга, чтобы расшифровать E2EE-конверт.
- Прямые сообщения не «протекают» посторонним (фильтр и в live-доставке, и в
  snapshot/backlog).
- Свои сообщения можно править (флаг «изм.») и удалять (удаление также admin);
  правка/удаление реплицируются мешком и live-пакетам.
- Файлы/фото (📎, E2EE, до 8 МБ) и голосовые (🎤, `audio/webm` до 5 мин):
  байты sealed случайным fileKey, ключ — в v2-конверте; снапшот несёт метадату,
  байты грузятся по открытию (`GET /api/v1/files`).
- Снапшот несёт новейшие 300 сообщений; старше — «Загрузить более ранние»
  (`GET /api/v1/messages?before_id=&limit=`); поиск — по расшифрованному локально.
- «Печатает…» (только директ) и `✓/✓✓` прочтения — эфемерные presence-хинты,
  офлайн не доставляются и не журналируются.

### Звонки (1:1)
- Кнопка «Позвонить» — только онлайн-абоненту, на которого есть ключ.
- P2P WebRTC: SDP/ICE/ключ SFrame — внутри E2EE-конверта; только host-кандидаты
  (одна ЛВС). Онлайн-статус — через `presence`.
- UI: ringing/calling/connecting/in-call, значок «E2EE»/«не E2EE» (SFrame
  отсутствует → DTLS-only).
- История вызовов (входящие/исходящие/пропущенные/офлайн) — локально на аппарате
  в доке «Рация» (`pp.calllog.<позывной>`, кап 50); сервер сигналинг не хранит.

### Рация (PTT)
- Собери группу до MAX_MEMBERS (6 в UI панели), «Начать сеанс»;
  full-mesh: каждый держит соединение с каждым.
- «ГОВОРИТЬ (удерживать)» — микрофон через `replaceTrack`, слышат все
  участники; не-говорящие приглушаются. Для перчаток — «Фикс передачи»
  (слайд пальца не рвёт эфир).
- Очередь эфира (последние 5 говоривших) — в доке сеанса.
- Сессия эфемерна, узел её не журналирует.

## 4. Сценарии админа

- **Выпуск ключей** (§2), **отзыв/возврат** (§2).
- **Проверка журнала**: Абоненты→Журнал→«Проверить целостность» → узл пере-
  вычисляет hash-цепочку, выводит «OK / TAMPERED».
- **Экспорт журнала**: «Экспорт» → JSON-мешок (можно выгрузить «после TS»).
- **Импорт мешка**: Абоненты→Импорт → загрузка файла → проверки подписи/цепи/
  непрерывности → воспроизведение событий; отчёт `added/skipped/head`.
- **Статистика** (`/api/v1/admin/stats`): счётчики абонентов/меток/сообщений/
  тревог/зоны.

## 5. Нештатные и аварийные сценарии

### Потеря флешки-ключ-носителя
- Узел с watchdog'ом гасится; ключ затёрт. Базу можно открыть только полным
  ключом из сейфа (`-rescue-out`): `pp run -key <rescue>`.
- Если сейф-копии нет и потеряна половина — **данные недоступны** (повтор
  неизбежен; журнал поможет аудиту при будущем меш-обмене). Поэтому
  `-rescue-out` на этапе init обязателен для серьёзного использования.

### Абонент потерял/скомпрометировал ключ
1. Админ отзывает позывной (немедленно: лайв-кик, блоку вручную, блокировка
   доставки, drop из snapshot).
2. Выпускается новый ключ с тем же/другим позывным.
3. Старые E2EE-конверты данному абоненту больше не расшифруются (ключ другой),
   новые — шифруются на новый отпечаток.

### Перехват/подмена трафика
- Каждый пакет подписан; чужой callsign невозможен (ECDSA), повтор отсекается
  replay-guard, содержимое E2EE. Сноска: SFrame-медиа не прочитать даже
  релеющему узлу без груп-ключа.

### Дрейф часов офлайн-устройств
- Сервер с `-clock-calibrate` обучается смещению по **admin**-пакетам (EMA,
  пределы ±30 мин) — компенсирует ложные `ErrReplay` от «курящих» часов.

### «Флешка другого узла»
- `scanSticks` найдёт её, но `resolveUsbReuse` предложит только носители того же
  NodeID; чужие — в предупреждениях; если ни одной своей — ошибка с перечнем.
  Перезаписать чужой `pp.key` невозможно (usb_common.go:263-305).

## 6. Мультиузельная работа: перенос событий (sneaker-net)

Отдельные узлы работают изолированно (у каждого — свой реестр и vault).
Обмен событиями — **физическая перевозка мешков**:

```
узел A │ узел B
──────────────────────────────────────────────────────
admin A: journal-export -after <ts> -out bagA.json
        (физически: USB/карта/печать →) 
                          admin B: journal-import -in bagA.json
                                    (проверки: подпись/цепь/непрерывность,
                                     воспроизведение меток/сообщений/тревог/зон)
```
- Адресация в импорте: выполняются только события, совпадающие с локальным
  реестром (чьи подписи валидны). Чужие/отозванные — честно пропускаются
  (SkippedCtx/SkippedDup), журнал при этом идемпотентен.
- Непрерывность: мешок продолжается ровно с головы локального журнала
  (`localHead == entries[0].PrevHash`).
- Это же — естественный канал «переносимых меток/сообщений» между офлайн-узлами
  одной сети (например, из штаба в поле и обратно по неделям).

## 7. Офлайн-поведение (нет связи между узлом и абонентом)

- Узел копит всё в `packets` (delivered=0). Абонент при подключении получает
  snapshot + недоставленные пакеты (§2-3) и подтверждает их `ack`.
- Медиа (звонки/рация) требует одновременного онлайн обоих участников;
  офлайн-звонки невозможны по дизайну (нет записей аудио — защита приватности).
- Текстовые/карт-события сохраняются и доезжают при первом коннекте.

## 8. Точка отказа и инварианты

- **Единственная точка** — узел и его `vault.db` (потеря данных узла = потеря
  журнала). Это компенсируется: журнал-подтверждаемостью (hash-цепочка),
  резервными ключами (rescue), меш-переносом истории на другие узлы.
- Инвариант: **никогда не хранить весь мастер-ключ на узле; флешка — только
  половина**. «Не вынимайте флешку» — не рекомендация, а требование работы
  watchdog.
