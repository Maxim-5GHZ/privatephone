# privatephone — ПАК АСК (программно-аппаратный комплекс автономной связи и координации)

Автономная offline-система координации: карта меток + защищённый чат для группы.
Один статический бинарник (Go + встроенный React-интерфейс и офлайн-карта), база данных
зашифрована AES-256-GCM, мастер-ключ базы — **из двух половин**: локальная `data/pp.local`
на диске машины + USB-половина `pp.key` на флешке; рабочий ключ живёт только в RAM процесса
(mlock) и при извлечении флешки мгновенно затирается.
Каждый пакет подписан закрытым ключом абонента (ECDSA P-256) и проверяется сервером;
неизвестные или неверно подписанные пакеты отбрасываются.
**Содержимое**: сообщения, маркеры, тревоги и зоны зашифрованы end-to-end (AES-256-GCM,
на каждый конверт — свой эфемерный ECDH-ключ, forward secrecy) — сервер видит только
обёртки-шифротекст.

Ноль зависимостей на хосте: без Docker, nginx, Node, внешних СУБД, без выхода в интернет.

## Принцип работы

```
Устройство оператора (сервер)
  vault.db ─── AES-256-GCM ───> ключ = SHA-256(pp.local ‖ pp.key)
                                half A: data/pp.local (на диске машины)
                                half B: pp.key на USB-флешке
                                рабочий ключ только в RAM (mlock), затирается при выдёргивании
  WebSocket store-and-forward: пакеты журналируются и доставляются при reconnect
  ECDSA: сервер проверяет подпись каждого пакета (anti-MITM, replay-guard ±10мин)

Браузеры абонентов (ЛВС / Wi-Fi / выносная точка)
  WebCrypto подписывает каждый пакет ключом PKCS#8 с флешки (file-picker)
  офлайн-карта Leaflet: тайлы из бинарника
```

## Мастер-ключ из двух половин (рекомендуемый путь)

Бинарник живёт в user-директории оператора (например `~/privatephone/pp`), данные — рядом
в `data/` (зашифрованная база, ключ оператора, внутренний CA, TLS-сертификат). **Флешка —
только носитель половины ключа** (аппаратный токен), на ней нет ни бинарника, ни базы:

- локальная половина — `data/pp.local` (0600, на диске машины);
- USB-половина — `pp.key` на флешке;
- мастер-ключ базы = `SHA-256(pp.local ‖ pp.key)`, материализуется **только в RAM**
  (mlock), на диск не пишется. Ни одна половина сама по себе базу не открывает.

1. Вставьте флешку и запустите бинарник из своей папки **двойным кликом** (`pp` / `pp.exe`).
2. Сервер **сам находит** флешку и **просит оператора подтвердить выбор** носителя
   (при нескольких флешках — выбрать номер). Если ключа нигде нет — первый запуск
   предложит создать половинки: `pp.local` рядом с данными и `pp.key` на флешке.
3. Дальше всё автоматически: зашифрованная база, ключ оператора `admin.pem`, внутренний
   CA и TLS-сертификат, HTTPS печатает в консоль адрес `https://<IP>:8080`.
4. Повторный запуск: без флагов подхватываются те же половинки.

Выдёргивание флешки во время работы: ключ затирается из памяти, сервер гасится за ~1
секунду. Вставили обратно и перезапустили — всё восстановится (теряются максимум
последние секунды). **Потеря флешки ИЛИ локальной половины делает базу неоткрываемой** —
храните их раздельно, а полный ключ — резервной копией в сейфе.

Резервный режим с одним полным ключом: `-key FILE` (при `init` можно сохранить полный ключ
`pp init -rescue-out FILE`), `-data` по умолчанию — `<папка бинарника>/data`. Для
неинтерактивного запуска (сервис/фон): одна флешка с ключом выбирается автоматически,
несколько — ошибка с требованием явного `-key`.

Сборка бинарников под все платформы — `make cross` (binary в `build/pp-<os>-<arch>[.exe]`);
это инструмент разработчика, оператору достаточно готового одного файла.

## Сборка

Требуется: Go ≥ 1.26, Node ≥ 20 (только для сборки UI, не для выполнения).

```bash
make build   # ui + placeholder tiles + single binary -> build/pp
make cross   # linux/amd64 linux/arm64 windows/amd64 darwin/arm64 -> build/pp-*
make test    # go test ./... (e2e: подписанный REST+WS контур) + vitest для crypto
make cover   # порог покрытия Go: >=80% по всем internal/... пакетам
make vet
```

## Первое развёртывание

1. Скопировать готовый бинарник в директорию оператора (например `~/privatephone/pp`).
2. Вставить USB-флешку — она станет носителем USB-половины ключа.
3. Инициализировать узел (сервер сам найдёт/подтвердит флешку; без `MASTER_USB` — схема
   с двумя половинами):
   ```bash
   make init                     # halves: data/pp.local + pp.key на флешке
   # или резервный режим с полным ключом:
   make init MASTER_USB=/mnt/usb/rescue.key
   ```
   `init` записывает: половины мастер-ключа (локальная `data/pp.local` + USB `pp.key`),
   `admin.pem` (ключ оператора для создания абонентов), внутренний CA и TLS-сертификат.
4. Запустить сервер на машине оператора:
   ```bash
   make run                      # половинки подхватываются автоматически
   # или явный полный ключ (резервный режим):
   make run MASTER_USB=/mnt/usb/rescue.key PORT=:8080
   ```
   Сервер хранит БД в `data/vault.db` (зашифрованной AES-256-GCM). Рабочая копия — в RAM
   (`/dev/shm`). При извлечении USB-флешки сервер затирает ключ и гасится за ~1 сек.

`init` дополнительно создаёт **внутренний CA** (`data/ca.crt` + `data/ca.key`) и подписанный
им сертификат узла (`data/tls.crt` + `data/tls.key`, SAN = `-ips`). Один корневой сертификат
покрывает весь узел/полигон — см. «HTTPS/WSS». Флаг `-no-tls` пропускает генерацию
сертификатов.

## Абоненты

- Оператор открывает UI (админ) → «Абоненты» → выдать позывной+роль.
- Браузер скачивает `<callsign>.prv.pem`, абонент копирует его на свою флешку.
- Вход в UI: выбрать файл ключа, ввести позывной. Все REST и WS пакеты подписываются.

## E2EE содержимого

Ключ абонента (PKCS#8 P-256 с флешки) используется дважды: как ECDSA — для подписи пакетов,
и повторно импортируется браузером как **ECDH** — для выработки ключей сообщений. Публичные
ключи уже есть в реестре, поэтому сервер участвует в доставке, но не знает секретов.

- Формат конверта: `{v:2, alg:"A256GCM", epub, iv, c, k:[{to,salt,iv,ek}]}` — msg-key шифрует
  контент, для каждого получателя msg-key заворачивается в свой `ek`. ECDH-секрет берётся
  из **эфемерного** ключа отправителя (`epub`, свежий на каждый конверт) и статического
  ключа получателя через HKDF("pp-e2ee/v2"): компрометация статического ключа в будущем
  не вскрывает прошлых конвертов (forward secrecy). Легаси-строки `{v:1,...}` (static-static
  ECDH, HKDF "pp-e2ee/v1") по-прежнему расшифровываются как запасной путь к старым записям.
- **Самозавёртка**: автор всегда включён в получателей, поэтому и свои собственные пакеты
  он дешифрует тем же путём, что и чужие.
- Сервер непрозрачен: поля-заглушки (`lat/lon=0`, `type/name="enc"`) + конверт в `desc`/`body`/
  `points`/`text`; подпись идёт по канону шифротекста, так что журнал остаётся
  tamper-evident без вскрытия контента. Роутинг сообщений (`recipient`) остаётся читаемым.
- Обновления меток/зон несут полный новый контент (зашифрованный), сервер ничего не «мёржит».
- Кэш расшифровки в UI адресуется **контент-хэшем** (§ `frontend/src/crypto/content.ts`),
  а не `(sender, nonce)`: update переиспользует nonce, но несёт свежий конверт.
- Кнопка **fp** в админке показывает отпечаток ключа оператора (`shape`: 8 hex) для
  сверки out-of-band; бейдж **E2EE** — состояние загрузки ECDH-ключа после входа.

## HTTPS/WSS и звонки (WebRTC)

Микрофон/камера доступны браузеру только в secure context, поэтому сервер умеет работать
по HTTPS, а звонок — настоящий P2P WebRTC между браузерами (сигнализация летит через наш
подписанный WS, медиа — напрямую, без TURN нужна одна ЛВС):

1. При `init` указать IP-адреса машины оператора в ЛВС — они попадут в SAN сертификата:
   ```bash
   make init IPS=192.168.1.10,10.0.0.5
   # резервный режим с полным ключом:
   make init IPS=192.168.1.10,10.0.0.5 MASTER_USB=/mnt/usb/rescue.key
   ```
   Узел получает ключ своего внутреннего CA (`data/ca.crt`, `data/ca.key`) и подписанный
   им сертификат `data/tls.crt` (+`data/tls.key`) — цепочка поддерживается из коробки.
2. Запускать с `-tls` (Makefile: `make run` уже включает флаг):
   ```bash
   make run PORT=:8443
   # или явный полный ключ:
   make run MASTER_USB=/mnt/usb/rescue.key PORT=:8443
   ```
3. Один раз импортировать `data/ca.crt` как доверенный корень на каждое устройство
   абонента (управление сертификатами ОС; готовый скрипт — `scripts/install_ca.sh`),
   затем открывать `https://192.168.1.10:8443`. Один корень покрывает и WSS-сигнализацию,
   и secure context для WebRTC — отдельный импорт `tls.crt` не нужен.

Без импорта сертификата браузер покажет предупреждение (можно «продолжить» для http/ws,
но `getUserMedia` и WebRTC работать не будут). Директы/групповые чаты идут через сервер
(store-and-forward, маршрутизация по получателю, контроль доступа сервером); звонок —
между абонентами напрямую, содержимое медиа-потока сервер не видит.

### E2EE медиа-канала (SFrame)

Медиа звонка и рации дополнительно шифруются **SFrame** (AES-GCM по кадрам, ключ на сеанс) —
второй E2EE-слой поверх DTLS/SRTP: даже если SRTP-ключи транспорта когда-либо станут
доступны ретранслятору/перехватчику (или медиа пойдёт через будущий SFU), кадры, прошедшие
через узел, остаются запечатанными ключом сеанса и проверяемыми по аутентификационному тегу:

- 1:1 звонок: групповой ключ `sframeKey` как часть E2EE-сигналинга (`sealSignal`); каллер
  берёт `{out:1, in:2}`, ответивший — `{out:2, in:1}` (направленные keyId, WebRTC-суффикс).
- Рация (PTT): общий ключ сеанса для всех участников (`mirror:false`, один keyId);
  полная сетка peer-соединений.
- Сверка отпечатка абонента перед началом разговора обязательна — иначе возможен
  man-in-the-middle (сервер честно прозрачен, но ключи конференции идут через него).
- Если браузер не даёт безопасные WebRTC-трансформы (encoded insertable streams),
  UI честно помечает канал **«не E2EE»** и отключает микрофон/сервер зашифровать не может.

## Журнал целостности и отзыв абонентов

- **Отзыв (CRL)**: admin отзывает позывной (`/api/v1/ca/revoke`, kind `revoke_subscriber` / `unrevoke_subscriber`).
  Отозванный ключ перестаёт проходить проверку подписи (вход, REST, WS), активное
  соединение немедленно разрывается. Кроме того, hub не доставляет **новый** шифротекст
  отозванным даже за мгновения до разрыва (in-memory CRL-кэш), а клиенты-отправители
  не заворачивают конверты на отозванные позывные. Отображение статуса — во вкладке «Абоненты».
- **Криптографический предел отзыва**: содержимое, которое отозванный абонент уже получил
  до отзыва, вернуть «назад» нельзя — получатель мог сохранить конверт и свой ключ.
  Эфемерные ключи Фазы 5 (v2) не позволяют при этом расшифровать то, что ушло **после**
  отзыва (свежих обёрток ему никто не делает), и не вскрывают чужих сообщений даже при
  компрометации его статического ключа в будущем.
- **Tamper-evident журнал**: каждый принятый пакет пишется в `packets` с
  детерминированным id (sender|kind|nonce|ts) и хэшем предыдущего (`prev_hash`),
  образуя цепь SHA-256 в порядке приёма. Проверка: вкладка «Журнал» (кнопка
  «Проверить целостность») или CLI:
  ```bash
  make build
  ./build/pp verify-journal -data ./data   # exit 1 при повреждении (ключ — из половин)
  ```
- Экспорт журнала (`GET /api/v1/journal`, только admin, kind `journal_export`)
  отдаёт полные подписанные пакеты — это основа sneaker-net переноса между
  разобщёнными полигонами и резервного восстановления (Фаза 4).
- Админ-действия сами журналируются с получателем `@system` (все видны в журнале,
  никому не реплеются в бэклог).

## Расхождение часов (реплей-гард)

Отклонение времени устройства абонента от узла в пределах ±10 минут пропускается
реплей-гардом (окно проверки). Если часы «уехали» сильнее, пакеты абонента отклоняются
как stale/повторные. Узел умеет **калибровать** реальный сдвиг автоматически:

```bash
./build/pp run -data ./data -tls -clock-calibrate
# ограничить допустимый сдвиг вручную, если известно, что часы сети шалят:
./build/pp run ... -clock-skew 5m
```

- `-clock-calibrate`: узел учит смещение по временным меткам **admin**-пакетов (EMA,
  clamp ±30м, сходится за ~минуту) и применяет к проверкам остальных абонентов;
  доверяются только админ-ключи, обычные абоненты влиять на оценку не могут.
- `-clock-calibrate -clock-skew N`: жёсткое окно N поверх калибровки (по умолчанию 10м).
- Текущую системную дату узел печатает в лог при старте — сверяйте с устройствами.

## Чат и маркеры

- **Общий чат** — всем абонентам. **Прямые сообщения** — адресат указывается в рельсе чата.
- **Групповые чаты** — создаются на лету (выбор получателей), пересылаются тем же
  store-and-forward, видимы только участникам.
- Адресность хранится в `packets.recipient` (`''` = всем, `"callsign"` = директ,
  `["a","b"]` = группа); снапшот и backlog фильтруются по получателю.
- Маркеры карты: у каждого есть автор; переименование/удаление — только автор или admin
  (`marker_update`/`marker_delete` по связке `sender+nonce`). Метки старше 24 ч можно
  скрыть фильтром в UI.

## Тревоги и команды

- Кнопки **SOS / СБОР** на панели карты поднимают общую тревогу (kind `alert`); «Инфо» —
  менее заметный вариант. Тревога широковещательна: попадает в журнал с получателем `''`
  и реплеется из backlog всем (включая тех, кто был офлайн в момент обьявления).
- **Баннер тревоги** (красный SOS с пульсацией / оранжевый СБОР) висит в шапке у всех;
  звуковой сигнал — через WebAudio. Кнопка **«Принял»** (`alert_ack`, `@system` в журнале —
  только аудит, никому не реплеется; счётчик подтверждений берётся из снапшота).
- **«Отбой»** (`alert_clear`) — только автор или admin; после отбоя баннер исчезает у всех.

## Зоны и полигоны

- Кнопка **«Полигон»** включает режим рисования: клики по карте задают вершины контура,
  «Завершить» — открывает форму названия/цвета и подписывает пакет `zone`.
- Зоны — общая ситуационная обстановка (в журнале с получателем `''`, реплеются всем).
- Переименование/перекраска и удаление — только автор или admin (`zone_update`/`zone_delete`
  по связке `sender+nonce`), как и метки.

## Рация (PTT, push-to-talk)

- Кнопка **«Рация»** в шапке открывает панель: выбор абонентов из сети (до 6 всего)
  и **«Начать сеанс»**. Каждый участник держит прямое WebRTC-соединение с каждым
  (полная сетка, медиа идёт мимо сервера — только на одной ЛВС, как и звонок).
- Сигнализация — подписанные пакеты `ptt_start/ptt_offer/ptt_answer/ptt_ice/ptt_talking/ptt_end`,
  сервер только перенаправляет их адресату(ам) (`to` — позывной или массив), как и
  сигналинг звонка. Сеансы эфемерны: в журнал целостности не пишутся.
- Кнопка **«ГОВОРИТЬ (удерживать)»** включает микрофон у говорящего; у остальных
  заглушаются прочие динамики, звук активного абонента остаётся. «Говорит: …» —
  индикация в панели. Никто не получает чужой микрофон постоянно (walkie-talkie).
- Абоненты, покинувшие сеть, автоматически выпадают из сеанса по разрыву соединения.

## Резервное копирование и sneaker-net (перенос журнала)

Узел полностью восстанавливается из **полного мастер-ключа** (резервная копия в сейфе,
`pp init -rescue-out`) — либо из **обеих половин** — и **зашифрованного `data/vault.db`**.
Резервной копии `vault.db` достаточно для полного восстановления (внутри — абоненты,
журнал, метки, сообщения, тревоги, зоны).

```bash
make build
# полное резервное копирование (узел должен быть остановлен):
./build/pp vault-backup -data ./data -out backup.tar.gz
# восстановление на свежую машину: локальной половины там нет, нужен полный ключ
./build/pp vault-restore -in backup.tar.gz -key /srv/safe/rescue.key -data ./data
# (на той же машине достаточно половин: ./build/pp vault-restore -in backup.tar.gz -data ./data -force)
# после restore узел открывается и журнал автоматически проверяется целостностью
```

**Sneaker-net между разобщёнными узлами** — перенос журнала «мешком» на флешке
(полный дамп или инкрементальный по `-after`, узлы могут не иметь сети между собой):

```bash
# на северном узле:
./build/pp journal-export -data ./data -out north.json
# на южном узле:
./build/pp journal-import -data ./data -in north.json
```
(`-key <файл>` — полный ключ, если нужен резервный путь вместо половин.)

- Импорт **проверяет**: (1) мешок продолжает локальную цепь хэшей (или это полный первый
  дамп); (2) внутренняя цепь самого мешка не разорвана; (3) каждая подпись сверяется с
  публичными ключами, зарегистрированными на принимающем узле. Любая порча — весь мешок
  отклоняется, ничего не записывается (все-или-ничего).
- Те же ключи абонентов должны быть заведены на обоих узлах (спецификация регистрации
  остаётся узловой, ключи разворачиваются одинаково); **отзывы (CRL) переносятся в мешке
  автоматически** — импортированное `revoke_subscriber` применяется к локальному реестру.
- Идемпотентность: повторный импорт того же мешка — no-op (детерминированный id пакета);
  два соседних мешка (частичный потом следующий) склеиваются в одну непрерывную цепь.
- Экспорт в Web UI (вкладка «Журнал») и REST `GET /api/v1/journal` (kind `journal_export`)
  дают тот же формат мешка.

## Дашборд оператора (админ)

Вкладка **«Админ»** (доступна только role `admin`): компактная сводка — число абонентов
(и отдельно активных/отозванных), онлайн сейчас, активные тревоги, размер и «голова» журнала;

- **«Абоненты»** — список с ролями/статусом отзыва (отозвать/вернуть, работает и через CRL).
- **«Журнал»** — «Проверить целостность» (пересчёт хэш-цепи) и «Экспорт мешка» для sneaker-net.
- **«Импорт»** — выбрать `journal-bag.json` с флешки, REST-импорт (`/api/v1/journal/import`) с
  отчётом (добавлено / дубли / отклонено) — тот же путь, что у CLI `journal-import`.
- Статистика приходит из `GET /api/v1/admin/stats` (kind `admin_stats`, только admin).

## Ограничения MVP (честно)

- `mlock` удерживает ключ в невыгружаемой памяти: Linux/macOS — `mlock(2)` (best-effort),
  Windows — `VirtualLock` на странично-выровненных буферах; на остальных ОС — no-op.
- Ключ для браузера выбирается через file picker (стандарт); автодоступ к USB-флешке
  браузер не имеет — абонент выбирает файл каждый сеанс.
- Watchdog проверяет файл USB-половины ключа раз в 1 сек. Монтирование USB обычно требует
  прав root (systemd unit / sudo); `make run` запускает сервер в штатной схеме половин.
- Replay-guard: окно ±10 минут по часам; при расхождении — `-clock-calibrate`/`-clock-skew`
  (см. «Расхождение часов»).
- Тест e2e использует случайный порт; dev/prod — свой порт во флагах `-port`.
- Внутренний CA узла (`data/ca.crt`): доверенный корень нужно один раз импортировать на
  каждое устройство абонента (`scripts/install_ca.sh`); без импорта — предупреждение браузера.
- WebRTC без TURN/STUN: работает в одной ЛВС (host-кандидаты); между разными сетями
  звонок не пройдёт. Один активный звонок на клиента, без ICE-restart.
- **Контент (сообщения, маркеры, тревоги, зоны) шифруется end-to-end** (см. «E2EE содержимого»).
  Медиа звонков/рации — P2P WebRTC (сервер его не видит) плюс **SFrame E2EE** ключом сеанса
  (см. «HTTPS/WSS»); если браузер не даёт encoded transforms, канал честно помечается
  «не E2EE» и медиа в нём не включается.

```
server/cmd/gentiles    генератор placeholder-тайлов z0-5
frontend/src           React: Login / Карта / Чат / Админ, WebCrypto подпись + E2EE

```

## Известные ограничения / безопасность

Это учебно-опытный прототип под ТЗ ГОСТ-стиля. Для боевого ПАК требуются: аппаратный
HSM/чип для ключей, аудит крипто-канона, обфускация бинарника, цифровая подпись самого
бинарника, прогон на Astra Linux, проверка отказоустойчивости питания (kill при потере
vault в RAM безопасен: БД перешифровывается только явным VACUUM + persist каждые N сек).
